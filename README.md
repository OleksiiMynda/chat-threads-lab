# Лабораторна 2. Мережевий чат: сокети, потоки, синхронізація, файловий журнал

Центральний сервер приймає TCP-підключення клієнтів на `127.0.0.1`, обробляє кожного
в окремому потоці та пересилає повідомлення всім іншим клієнтам. Усі події пишуться
у текстовий файл. Є також засоби для дослідження з'єднань через `netstat -ano` / PowerShell.

> Виконав: _ПІБ, група_ (заповнити)

## Запуск

Потрібен лише Python 3.10+ (сторонні бібліотеки не потрібні).

```powershell
python server.py                    # сервер; порт вибирає ОС, його буде виведено в консоль
python client.py --port 60370       # клієнт (порт з виводу сервера); можна запускати в кількох вікнах
python client.py --port 60370 --name alice
```

Команди клієнта: `/users` - хто онлайн, `/quit` - вийти (також Ctrl+C). Сервер зупиняється по Ctrl+C.

Додатково:

```powershell
python stress_test.py               # автотест: багато клієнтів, обриви з'єднань, перевірка журналу
python file_io_experiment.py        # дослідження запису у файл з кількох потоків
.\inspect_server.ps1                # PID, порт і TCP-з'єднання сервера (netstat -ano + PowerShell)
.\inspect_server.ps1 -Watch 2       # те саме в циклі кожні 2 с
```

## Структура рішення

| Вимога завдання | Де реалізовано |
|---|---|
| Серверний сокет, `127.0.0.1`, довільний вільний порт | `ChatServer.__init__`: `bind((host, 0))` - порт 0 означає "будь-який вільний", реальний порт береться з `getsockname()` |
| Очікування підключень | `ChatServer.serve_forever`: цикл `accept()` (з таймаутом 0.5 с, бо в Windows блокуючий `accept` не реагує на Ctrl+C) |
| Окремий потік на клієнта | `handle_client`, запускається як `threading.Thread` для кожного `accept` |
| Підключення клієнта, надсилання, отримання, відключення | `client.py`: основний потік читає ввід і шле рядки; потік-приймач `receive_loop` показує чужі повідомлення; `/quit`, Ctrl+C |
| Спільний список клієнтів + `threading.Lock` | `ChatServer.clients` + `clients_lock`; `add_client`, `remove_client`, `snapshot` |
| Несподівані відключення | `handle_client` ловить `OSError` (скидання з'єднання тощо); `broadcast` видаляє клієнта, якщо відправлення не вдалось |
| Запис у файл з кількох потоків | `ChatLogger` (власний `Lock` на запис + `flush`) |

**Протокол.** Текст UTF-8, одне повідомлення - один рядок (`\n`). Перший рядок від клієнта -
нікнейм (якщо зайнятий, сервер додає суфікс: `bob` -> `bob_2`). Довжина рядка обмежена 4096 байтами.

### Рішення щодо синхронізації

- **Один замок на спільний список** (`clients_lock`). Він утримується тільки на час самої операції зі списком
  (додати / видалити / скопіювати). Розсилка працює так: під замком робиться **копія** списку (`snapshot`), а самі
  `send` виконуються вже **без** замка. Інакше один повільний клієнт, на якому заблокувався `sendall`,
  зупинив би весь сервер (ніхто не міг би підключитись чи відключитись).
- **Окремий `send_lock` у кожного клієнта.** Два потоки можуть одночасно розсилати повідомлення одному й тому
  самому адресату; без замка байти двох повідомлень могли б перемішатись у сокеті.
- **Видалення клієнта відбувається рівно один раз.** Клієнта можуть спробувати завершити одразу два місця:
  його власний потік (обрив) і розсилка, що наштовхнулась на мертвий сокет. `remove_client` повертає `True` лише тому,
  хто справді видалив запис, тому лише він пише `LEAVE`/`DISCONNECT` у журнал і розсилає сповіщення.
- **Порядок замків без вкладення.** `clients_lock`, `send_lock` і замок журналу ніколи не утримуються
  одночасно (вкладених захоплень немає), тому взаємне блокування (deadlock) неможливе.

### Обробка несподіваних відключень

| Ситуація | Що бачить сервер | Що робить |
|---|---|---|
| Клієнт надіслав `/quit` | команда | `LEAVE` у журнал, розсилка "залишив чат" |
| Клієнт закрив сокет без `/quit` | читання повертає порожній результат | `DISCONNECT`, видалення зі списку |
| Процес клієнта вбито / мережа скинула з'єднання | `ConnectionResetError` | `DISCONNECT (ConnectionResetError)`, видалення |
| Клієнт підключився й мовчить | таймаут 30 с на нікнейм | з'єднання закривається, `DROPPED` |
| Розсилка до клієнта з мертвим сокетом | `OSError` у `sendall` | клієнт видаляється так само, інші не зачеплені |
| Нерозпізнані байти / надто довгий рядок | `errors="replace"`, обмеження 4096 байт | рядок усічується, з'єднання не падає |

## Перевірка

`stress_test.py` піднімає сервер у фоновому потоці та 8 "стабільних" ботів, які одночасно шлють по 50 повідомлень,
плюс 3 "аварійні" боти, які рвуть з'єднання через `SO_LINGER=0` (TCP RST, як при падінні процесу).
Перевіряється: кожен стабільний бот отримав усі 350 повідомлень від інших; спільний список після всього порожній;
у журналі немає пошкоджених рядків; `JOIN = LEAVE + DISCONNECT`. Типовий результат (3 запуски поспіль - без помилок):

```
[OK] підключено 11 з 11 клієнтів
[OK] кожен стабільний бот отримав 350 повідомлень від інших стабільних
[OK] спільний список клієнтів після відключення всіх: 0 (очікується 0)
[OK] журнал: 450 рядків, пошкоджених: 0
[OK] MSG від стабільних у журналі: 400 (очікується 400)
[OK] CONNECT: 11, JOIN: 11, LEAVE: 8, DISCONNECT: 3
[OK] JOIN = LEAVE + DISCONNECT (11 = 11) - ніхто не оброблений двічі й не загублений
```

Ручний сценарій з трьома клієнтами (alice, bob, carol) - у [sample_chat_log.txt](sample_chat_log.txt).

## Дослідження процесу та з'єднань (netstat / PowerShell)

Сервер сам виводить свій PID і порт при старті. Для незалежної перевірки використовується
`inspect_server.ps1` або безпосередньо команди:

```powershell
netstat -ano -p TCP | Select-String ":60370\s"                  # усі рядки з портом сервера
Get-NetTCPConnection -OwningProcess 28152                       # з'єднання процесу за PID
Get-NetTCPConnection -State Listen -OwningProcess 28152         # який порт слухає сервер
Get-Process -Id 28152                                           # що це за процес
```

> Якщо Python встановлено з Microsoft Store, `python server.py` запускає **два** процеси: проміжний
> лаунчер (`WindowsApps\python.exe`) і справжній інтерпретатор (його дочірній процес). Порт слухає лише
> другий - саме його PID друкує сервер. У `inspect_server.ps1` вибирається процес, який має сокет у стані Listen.

### Результати спостережень (реальний запуск, сервер PID 28152, порт 60370)

**1. Після запуску, клієнтів немає** - одне прослуховування:

```
TCP    127.0.0.1:60370   0.0.0.0:0   LISTENING   28152
```

**2. Підключено 3 клієнти.** Кожне з'єднання видно **двічі** - з боку клієнта і з боку сервера (обидва кінці живуть
на одному комп'ютері). Клієнти - окремі процеси з власними PID і тимчасовими (ephemeral) портами; сервер для всіх
використовує той самий порт 60370:

```
TCP    127.0.0.1:50899   127.0.0.1:60370   ESTABLISHED   14568   <- клієнт alice
TCP    127.0.0.1:50900   127.0.0.1:60370   ESTABLISHED   20600   <- клієнт bob
TCP    127.0.0.1:50901   127.0.0.1:60370   ESTABLISHED   30524   <- клієнт carol
TCP    127.0.0.1:60370   0.0.0.0:0         LISTENING     28152
TCP    127.0.0.1:60370   127.0.0.1:50899   ESTABLISHED   28152   <- ті самі з'єднання, бік сервера
TCP    127.0.0.1:60370   127.0.0.1:50900   ESTABLISHED   28152
TCP    127.0.0.1:60370   127.0.0.1:50901   ESTABLISHED   28152
```

Підсумок: 1 `Listen` + 6 `Established` (3 з'єднання x 2 кінці).

**3. bob коректно виходить (`/quit`).** Обидва рядки bob (клієнтський і серверний) зникли зі стану `ESTABLISHED`:
серверний кінець пропав, а клієнтський перейшов у `TIME_WAIT` із PID `0` (власника вже немає):

```
TCP    127.0.0.1:50900   127.0.0.1:60370   TIME_WAIT     0
```

`TIME_WAIT` лишається у тієї сторони, що закрила з'єднання **першою** (тут клієнт: після `/quit` він викликає
`shutdown`). Стан потрібен, щоб запізнілі пакети старого з'єднання не потрапили в нове; у цьому вимірюванні він ще
тримався через 70 с (у Windows за замовчуванням близько 120 с).

**4. alice вбивають `taskkill /F`** (емуляція падіння клієнта). Усі рядки alice зникли одразу, **без** `TIME_WAIT`:
ОС закриває сокети завершеного процесу скиданням (RST), а не нормальним обміном FIN. Сервер у цей момент отримав
`ConnectionResetError` і записав `DISCONNECT`, carol побачила "alice відключився (обрив з'єднання)":

```
TCP    127.0.0.1:50900   127.0.0.1:60370   TIME_WAIT     0        <- лише залишок від bob
TCP    127.0.0.1:50901   127.0.0.1:60370   ESTABLISHED   30524
TCP    127.0.0.1:60370   0.0.0.0:0         LISTENING     28152
TCP    127.0.0.1:60370   127.0.0.1:50901   ESTABLISHED   28152
```

**Висновки.** (а) `netstat -ano` дозволяє зв'язати порт із процесом: PID у рядку `LISTENING` - це сервер, PID у рядках
з віддаленим портом 60370 - клієнти. (б) Кількість `ESTABLISHED` на сервері завжди дорівнює подвоєній кількості клієнтів
(по рядку на кожен кінець). (в) Коректне та аварійне відключення залишають різні сліди в TCP: `TIME_WAIT` проти миттєвого
зникнення, і сервер реагує на них різними подіями журналу (`LEAVE` та `DISCONNECT`).

## Запис у файл із кількох потоків

Журнал (`chat_log.txt`, формат `час | потік | подія | текст`) пишеться через `ChatLogger`. `file_io_experiment.py`
порівнює способи запису: 8 потоків x 2000 записів, кожен запис складається з кількох `write()` (як у наївному логері).
Медіана з 3 вимірів ([results_file_io.csv](results_file_io.csv)):

| Спосіб | Час, мс | Пошкоджених рядків із 16000 |
|---|---:|---:|
| без `Lock` | 98.7 | **13234** |
| `Lock` | 59.1 | 0 |
| `Lock` + `flush()` після кожного запису | 96.0 | 0 |
| `Lock` + `flush()` + `os.fsync()` | 6122.8 | 0 |
| відкриття/закриття файлу на кожен запис (під `Lock`) | 4815.6 | 0 |
| черга + один потік-писар | 32.6 | 0 |

Висновки:

- **Без `Lock` журнал псується**: частини різних записів вклинюються одна в одну (рядки розриваються й склеюються у
  неправильних місцях). Як і в лабораторній 1, між частинами запису вставлено `time.sleep(0)` ("вікно гонки"), бо через GIL
  потоки перемикаються рідко й без нього пошкодження траплялись би нерегулярно - помилка в коді та сама.
  Один виклик `write()` цілого рядка під GIL зазвичай не рветься, але покладатись на це не можна: запис, що складається
  з кількох викликів, уже не атомарний.
- **`Lock` робить запис коректним і не додає помітної вартості**: у цьому вимірі він навіть швидший за версію без
  замка (59 проти 99 мс), бо без замка потоки постійно перемикаються посеред запису. Не варто робити висновок, що
  замок "прискорює": головне - що 16000 записів лишились цілими, а час того ж порядку.
- **`flush()`** передає дані з буфера Python в ОС після кожного рядка: журнал актуальний при аварії процесу
  (ціна - близько +60%). Сервер використовує саме його (плюс `buffering=1`).
- **`fsync()`** вимагає фізичного запису на диск і повільніший майже на два порядки (~100 разів). Це захист від втрати
  живлення, для навчального чату він не потрібен (опція `--fsync` залишена для порівняння).
- **Відкривати файл на кожен запис** також дуже дорого (~80 разів повільніше).
- **Черга з одним потоком-писарем** найшвидша, бо потоки-клієнти не чекають на файл і не конкурують за нього.
  Недолік - складніше завершення (треба дописати чергу) і запис може відставати від подій. У лабораторній обрано
  простіший `Lock`, який відповідає завданню.

Час вимірюється в мілісекундах і залежить від диска та антивірусу: порівнюйте порядки величин.

## Обмеження

- Відправлення синхронне (`sendall`): клієнт, який перестав читати, але тримає з'єднання, рано чи пізно заблокує потік,
  що розсилає йому повідомлення (інші клієнти й список не страждають, але цей відправник "зависне"). Для реального
  сервера потрібна черга вихідних повідомлень на клієнта або `select`/`asyncio`.
- Нікнейми не автентифікуються, шифрування немає; сервер слухає лише `127.0.0.1`.
